### 1주차 — 베이스라인 스냅샷 + 데이터 진단 (완료)
- `raw_videos/` 6개 영상으로 현재 파이프라인 베이스라인 스냅샷 저장: `documents/baseline_eval/2026-09-25/`.
- 신규 `pipeline/diagnose_reliability_stats.py`: 결측 패턴, 이벤트별 공분산 조건수, 클러스터 분리도(실루엣) 진단.

### 2주차 — Mahalanobis 결합 스코어 (완료), 클러스터링 (최종 스킵)

- `run_analysis.py`: `mahalanobis_combined_score()` 신규 — 이벤트별 `combined_score.deviation_percentile`/`grade` 필드 추가(기존 `feedback.<feature>.*` 필드는 전혀 변경 없음, additive-only).
- **클러스터링(항목 3) 최종 스킵**: `trail_elbow_angle` 제외 재진단에서 처음엔 k=2 실루엣 0.4574로 유망해 보였으나, 실제로는 이상치 2명(pose 오검출)을 분리한 결과였음을 검증 과정에서 발견 — 이상치 제거 후 실루엣 0.06~0.11로 붕괴. 원본 342개 영상(`learning_video/golfdb_720p_slice`)을 확보했음에도 실제 클러스터 구조가 없어 skeleton 클러스터링은 구현하지 않음.
- 자체 재검토(코드 리뷰)로 이상치-오염 공분산 문제(캘리브레이션 median 7.6~27.2% → 수정 후 28.9~58.4%, 이론값 50%에 근접)와 circular 평균 버그를 발견/수정함.
- 상세 내용: `documents/feedback_v2_week2_notes.md`.
- 6개 영상 전부 기존 `z_score`/`grade` byte-level 동일함을 반복 검증(회귀 없음).

### 3주차 — 진행 중
- 범위를 **스윙 다이내믹스(이벤트 간 delta)만**으로 좁힘 — 문구 계층(B2/B3/B4)은 이번 3주차에서 제외하고 별도 계획으로 이후 다룸.
- 클러스터링이 스킵되어 원 계획의 "클러스터·다이내믹스 결과를 문구에 반영" 중 클러스터 부분은 자연히 제외됨.

## 배경 - v1 계획과의 관계

v1 계획(A: robust z-score/percentile, B: 피드백 문구 템플릿)은 숫자 계산 방식과 표현 방식만 다듬는 수준이라 구조적인 변화가 크지 않다는 판단 아래, 난이도가 다소 높아도 괜찮다는 전제로 더 실질적인 개선 방향을 다시 검토했다.

v1의 A, B 항목은 폐기하지 않고 v2의 상위 레이어로 그대로 재사용한다. v2는 그 아래에 구조적으로 더 의미 있는 계층을 추가하는 것이 핵심이다.

## 추천 방향

기존 A(통계)+B(문구) 계획 위에 다음 세 가지 구조적 개선을 추가한다. 모두 신규 영상 확보나 SwingNet 재학습 없이 기존 `pro_feature_raw.csv`만으로 구현 가능하다.

### 1. Robust Mahalanobis 결합 스코어

- 이벤트별 5개 feature(`trail_elbow_angle`, `lead_elbow_angle`, `shoulder_tilt`, `hip_tilt`, `spine_tilt`)를 독립 z-score가 아니라 공분산 행렬을 고려한 Mahalanobis distance로 결합 평가.
- "개별 feature는 정상 범위인데 조합이 이례적인" 자세를 잡아낼 수 있음(예: 어깨 기울기와 골반 기울기가 각각은 괜찮아도 그 조합이 프로 342명 분포에서 드문 경우).
- v1 이전 문서(`feedback_improvement_ideas.md`)에서 "통계적으로는 더 정교하지만 구현/검증 복잡도가 높다"는 이유로 제외했던 항목 — 이번엔 시간 여유를 반영해 재검토.
- 표본 부족 시 공분산 역행렬이 불안정할 수 있어 Ledoit-Wolf shrinkage 또는 정규화 적용 검토.

### 2. 이벤트 간 변화량(스윙 다이내믹스) 비교

- `video_id`로 이미 연결된 8이벤트 시퀀스에서 구간별 delta(예: Address→Top의 hip_tilt 변화량, Top→Impact의 spine_tilt 변화량)를 계산.
- 342명의 구간별 delta 분포를 만들고, 사용자의 구간별 변화 패턴을 그 분포와 비교 — "정적인 자세"가 아니라 "스윙 중 움직임"을 평가하는 첫 단계.
- 논문2(Park, 2023) 방식인 DTW 전체 궤적 비교는 342개 프로 영상 재확보 + 프레임 단위 pose 재추출이 필요해 리소스 문제로 제외됐던 항목인데, 이 방식은 기존 CSV만으로 구현 가능한 경량 대체안.

### 3. 프로 유형 클러스터링 → 개인화된 비교 기준

- 342명 프로를 스윙/체형 유형별로 K-means 등으로 클러스터링(전체 feature 벡터 또는 이벤트별 벡터 기준, 1주차 진단에서 결정).
- 사용자와 가장 가까운 클러스터를 찾아, 그 클러스터의 통계와 medoid skeleton으로 비교 — 전역 평균이 아니라 "나와 비슷한 타입의 프로"와 비교.
- 스켈레톤 이미지 비교 기능(`skeletons/` 출력)은 그대로 유지되고, 비교 대상만 전역 medoid에서 클러스터별 medoid로 교체된다.
- `pro_reference_skeletons.json` 포맷을 클러스터별로 확장해야 하며, 기존 필드는 하위 호환을 위해 유지하고 버전 필드를 추가한다.

### 4. (수정) B2 + B3(변경) + B4 문구 개선

- v1 계획의 편차 크기별 문장 강도(B2), 템플릿 다양화(B4)는 그대로 재사용.
- **B3는 방향 전환**: "정직한 순위 문구"(원인 해석 없이 순위만 명시)에서 `feedback_improvement_ideas.md`의 B1(도메인 지식 매핑 테이블)에 가까운 방식으로 변경 — 순위 대신 **원인 설명 + 교정 해결법**을 제공.
  - 도메인 지식 소스: 골프 코칭 일반 지식(퍼블릭 도메인 수준의 스윙 이론, X-factor/운동 체인 등)으로 초안 작성. 실제 사용자에게 배포하기 전에 반드시 검수 단계를 거친다(구현 완료 ≠ 배포 가능, 검수 통과가 배포 조건).
  - 범위: **1단계는 단일 이벤트 기준**으로만 원인/해결법을 매핑한다. `(event, feature, deviation_direction)` 조합 → `{원인 설명, 교정 드릴}` 형태의 매핑 테이블 하나로 구현 가능하며, v2 항목 1~3(Mahalanobis/다이내믹스/클러스터링) 완성 여부와 무관하게 독립적으로 작업 가능.
  - **백로그(이번 범위 제외)**: 이벤트 간 연쇄 원인 설명("백스윙이 늦어서 임팩트가 이렇다" 같이 두 개 이상의 이벤트에 걸친 원인)은 v2 항목 2(이벤트 간 delta 다이내믹스)가 먼저 구현되어야 정확도가 나오므로, 이번 4주 일정에는 포함하지 않고 다음 단계 작업으로 남겨둔다.
- 위 1~3번 결과를 반영해 "당신과 비슷한 스윙 타입의 프로 N명 중 상위 X%에 해당합니다" 같은 순위 문구는 B3 대체 이후에도 부가 정보로 유지 가능(원인 설명 문장 뒤에 덧붙이는 방식).
- 사용자에게 보이는 출력 문구만 바뀌고, 내부 계산(통계값, 등급, 클러스터 결과)을 담는 데이터 구조 자체는 A/1~3번 레이어가 그대로 사용된다 — 문구 계층은 최종 표현 담당일 뿐 계산 로직을 바꾸지 않는다. 단, 원인/해결법 매핑 테이블은 계산 로직이 아니라 별도의 정적 지식 데이터이므로 이 레이어에 새로 추가된다.

### 5. (선택) C1 - 프레임 윈도우 median

- SwingNet checkpoint 배치가 예정되어 있어, 이벤트 프레임 ±3~5프레임의 각도값 median으로 안정화하는 것도 이번 범위에 포함할 여지가 있음.
- 구현이 쉬워 4주차 여유 시간에 포함 가능한 선택 항목으로 분류.

## 4주 일정

### 1주차 - 베이스라인 스냅샷 + 데이터 진단
- v1 계획의 Phase 0(현재 방식 베이스라인 스냅샷 저장)을 그대로 실행 — `documents/baseline_eval/<날짜>/`에 `analysis.json`/`feedback_table.csv`/`feedback_ko.txt` 보관.
- 데이터 진단: feature별/이벤트별 결측 패턴 확인, 클러스터 분리도(실루엣 스코어) 확인, 공분산 행렬 조건수(condition number)로 Mahalanobis 적용 가능 여부 판단.
- 결정 게이트: 클러스터 분리가 뚜렷하지 않으면 3번(클러스터링)을 스킵하고 1, 2번만 진행하는 것으로 축소.

### 2주차 - 결합 스코어 + 클러스터링 구현
- `compute_reliability_stats.py`에 이벤트별 공분산 행렬/역행렬(필요시 shrinkage) 계산 추가, Mahalanobis 결합 스코어 구현.
- 클러스터링 구현: `build_reference_skeletons.py` 확장 — medoid 선택을 전역 → 클러스터별로 교체. sklearn 추가 여부는 1주차 진단 후 결정(직접 k-means 구현 vs 의존성 추가).

### 3주차 - 스윙 다이내믹스 + 문구 반영
- 이벤트 간 delta 다이내믹스 비교 구현.
- `generate_feedback_report.py`의 B2/B3/B4 문구 계층에 클러스터·다이내믹스 결과 반영.

### 4주차 - 마무리
- (선택) C1 프레임 안정화 적용.
- pytest 단위테스트 작성(AAA 패턴) — MAD/공분산/클러스터 할당/delta 계산 각각.
- 1주차 베이스라인과 diff 비교로 회귀 검토.
- 문서 업데이트(`README.md`, 본 계획서 완료 표시).

## 리스크

| 리스크 | 가능성 | 완화 방안 |
|---|---|---|
| sklearn 미설치 — 클러스터링에 필요할 수 있음 | 중간 | scipy만으로 간단 k-means 직접 구현하거나 pixi에 `scikit-learn` 추가(사용자 확인 필요) |
| n=342, 결측 있는 상태에서 적정 클러스터 개수(k) 결정 어려움 | 중간 | 1주차 진단에서 실루엣 스코어로 검증, 애매하면 클러스터링 항목만 스킵 |
| Mahalanobis 계산 시 공분산 역행렬이 표본 부족으로 불안정 | 낮음~중간 | Ledoit-Wolf shrinkage 또는 정규화(regularization) 적용 |
| `pro_reference_skeletons.json` 포맷 확장으로 기존 소비 코드 영향 | 낮음 | 버전 필드 추가, 기존 필드는 하위 호환 유지 |
| 스윙 다이내믹스(delta) 분포도 결측/이상치에 영향받을 수 있음 | 낮음 | v1의 robust 통계(median/MAD) 방식을 delta 분포에도 동일 적용 |
| B3 원인/해결법 매핑 테이블의 골프 지식이 부정확할 수 있음 (기존 B1 리스크와 동일) | 중간 | 배포 전 검수 단계 필수화(구현 완료와 배포 가능은 별개 게이트로 취급). 1단계는 단일 이벤트 기준 조합만 다뤄 범위를 좁혀 검수 부담 축소 |

## v1(이전 구현) 대비 무엇이 왜 더 좋아지는지 상세 설명

### 결론부터: 무엇이 바뀌는가

이전 구현(현재 코드)은 **"각 항목을 따로따로, 정적인 한 시점만, 전체 프로 평균 하나와" 비교**한다. v2는 이 세 가지 전제를 모두 깨고 **"항목 간 관계를, 스윙 중 움직임까지, 나와 비슷한 유형의 프로와"** 비교하도록 바꾼다.

### 1. 지금 코드가 실제로 하는 일 (그라운딩)

`run_analysis.py:feedback_for_event` (487~556행)의 핵심 로직:

```
diff = value - pro_mean          # feature 1개, event 1개만 봄
z_score = diff / pro_std
grade = "Excellent" if |z|<=1.0 else "Good" if |z|<=2.0 else "Needs Improvement"
```

이걸 `REQUIRED_FEATURES`(5개) × `EVENT_NAMES`(8개) = 40번 **완전히 독립적으로** 반복한다. 서로 다른 feature/event의 값을 한 번도 같이 보지 않는다.

그리고 `build_reference_skeletons.py`는 342명 중 "이벤트별 통계에 가장 가까운 실제 프로 프레임 1개"를 골라 **전역 medoid 1개**만 만든다. 체형이나 스윙 스타일이 다른 사용자도 전부 이 skeleton 하나와 비교된다.

### 2. 이 구조의 구체적 한계 3가지

**한계 A — feature 간 관계를 무시함**

골프에서 흔히 말하는 **X-factor**(어깨 회전 - 골반 회전의 차이)처럼, `shoulder_tilt`와 `hip_tilt`는 프로 스윙에서 서로 강하게 연동되어 움직인다. 그런데 지금 로직은:

```
shoulder_tilt: z=0.5 -> Good
hip_tilt: z=0.5 -> Good
```

이렇게 각각 "Good"이 나오면 전체적으로도 문제없다고 판단한다. 하지만 프로 342명 데이터에서 두 값이 항상 "같은 방향으로 같이 움직이는" 관계였다면, 사용자가 "어깨는 +0.5, 골반은 -0.5" 식으로 **따로 노는 조합**일 때 이건 프로 분포에서 실제로는 매우 드문 케이스일 수 있다. 지금 방식은 이걸 절대 못 잡아낸다 — 두 숫자를 동시에 보지 않기 때문이다.

**한계 B — 정적 스냅샷만 보고 "움직임"을 안 봄**

`pro_feature_raw.csv`는 `video_id`로 8개 이벤트가 이미 연결된 시퀀스 데이터다. 그런데 `compute_reliability_stats.py`가 통계를 만들 때 이 연결 정보를 버리고 **이벤트별 marginal 분포(mean/std)만** 남긴다. 그 결과:

- 프로 A: Address hip_tilt = 0°, Top hip_tilt = 40° (변화량 40°)
- 프로 B: Address hip_tilt = 5°, Top hip_tilt = 35° (변화량 30°)

이 둘의 "Address 값 분포"와 "Top 값 분포"는 각각 정상 범위로 잡히지만, **변화량(다이내믹스) 자체의 분포**는 지금 어디에도 저장되어 있지 않다. 사용자가 Address도 Top도 각각 "정상 범위"인데 그 사이 변화가 프로답지 않게 뻣뻣하거나 과하게 크더라도, 지금 시스템은 두 이벤트를 독립적으로만 채점하므로 이걸 감지할 방법이 아예 없다.

**한계 C — 전체 평균 하나로 모든 사용자를 재단함**

체형·스타일이 다른 두 프로(예: 컴팩트한 스윙 vs 풀스윙)를 섞어서 만든 평균은 "실제로 존재하지 않는 중간 자세"가 될 수 있다. 이 평균 하나만 기준으로 쓰면:
- 특정 스타일 사용자에게는 std 폭이 실제보다 넓게 잡혀 진짜 문제도 "정상"으로 통과되거나(둔감),
- 반대로 정상적인 스타일 차이를 "교정 필요"로 잘못 지적할 수 있다(과민).

스켈레톤 시각 비교도 마찬가지로, 나와 체형이 다른 "평균적 프로" 한 명과만 겹쳐 보여주므로 비교 자체가 직관적이지 않을 수 있다.

### 3. v2가 각각을 어떻게 고치는지

| 한계 | v2 해결책 | 메커니즘 |
|---|---|---|
| A. feature 독립성 | Mahalanobis 결합 스코어 | `distance = sqrt((x-mean)ᵀ Σ⁻¹ (x-mean))`. 공분산 행렬 Σ가 "어깨-골반이 같이 움직인다"는 관계를 학습하고 있으므로, 그 관계를 깨는 조합에 자동으로 높은 이상치 점수를 부여함 |
| B. 정적 스냅샷만 사용 | 이벤트 간 delta 분포 비교 | `video_id`로 묶어 Address→Top, Top→Impact 등 구간별 변화량을 342명에서 재계산 → 사용자의 변화량을 이 분포와 비교. "위치"가 아니라 "움직임"을 처음으로 평가 대상에 포함 |
| C. 단일 전역 기준 | 클러스터별 medoid | 342명을 유형별로 나눠, 사용자와 가장 가까운 클러스터의 평균·std·medoid skeleton을 기준으로 사용 → 그룹 내 분산이 좁아져 진짜 편차에 더 민감해지고, 스타일 차이를 오탐하는 것도 줄어듦. 스켈레톤 비교도 나와 비슷한 유형과 겹쳐 보여 시각적으로 더 직관적 |

### 4. v1(A/B)과 상충이 아니라 보완인 이유

v1의 A(robust z-score/percentile)와 B(문구 개선)는 **"하나의 숫자를 얼마나 정확하게 등급 매기고, 얼마나 잘 표현하느냐"**를 다룬다. v2는 **"애초에 무엇과 무엇을 비교할 것이냐"**를 다룬다. 층위가 다르다:

```
v2 (무엇을 비교할지)          →  개별 z-score/percentile 대신
  ├─ Mahalanobis 결합 스코어      각 feature/구간별로 계산되는
  ├─ 이벤트 간 delta               "숫자" 자체는 v1의 A(robust
  └─ 클러스터별 기준                통계) 방식을 그대로 적용
                              ↓
v1-B (그 숫자를 어떻게 표현할지) →  "당신과 비슷한 스윙 타입의
                                   프로 대비 상위 X%" 식 문장 생성
```

즉 v2가 비교 대상과 비교 방식을 더 정교하게 만들고, 그 결과 나온 숫자를 v1-A 방식으로 등급화하고, v1-B 방식으로 문장화하는 구조다. 폐기되는 부분 없이 그대로 이어진다.

### 5. 요약

| | 이전 구현 | v2 |
|---|---|---|
| 비교 단위 | feature 1개 × event 1개, 독립 | feature 조합(공분산) + event 간 변화량 |
| 비교 기준 | 프로 342명 전체 평균 1개 | 사용자와 가장 가까운 클러스터 |
| 잡아낼 수 있는 문제 | "이 각도 하나가 범위 밖" | + "항목 조합이 프로답지 않음", "움직임 패턴이 프로답지 않음", "내 체형/스타일 기준으로도 벗어남" |
| 스켈레톤 비교 | 전역 평균 1개와 항상 동일 | 나와 비슷한 유형의 medoid와 비교 |

한 줄로: 이전 구현은 "이 숫자가 정상 범위인가"만 물었다면, v2는 "이 숫자들의 조합이, 이 움직임이, 나와 같은 유형의 프로 기준으로 정상인가"를 묻는다.
